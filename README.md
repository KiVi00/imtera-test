Шаги:

```bash

cd imtera-test
composer install
cp .env.example .env
./vendor/bin/sail up -d
./vendor/bin/sail artisan key:generate
```

## Парсинг Яндекс.Карт

> Это центральная часть задания, и на неё ушло больше всего времени.

### Что я пробовал сначала

Открыл карточку в браузере, посмотрел **Network** и нашёл эндпоинт для подгрузки отзывов:

https://yandex.ru/maps/api/business/fetchReviews?ajax=1&businessId=...&csrfToken=...&offset=0&limit=50

Наивно попробовал повторить этот запрос через `Http::get()` – с тем `csrfToken`, который лежит в `state-view`. Яндекс вернул **новый токен** вместо данных. Добавил `CookieJar`, retry – но получал новый токен снова и снова.

Как я понял позже, правильный `csrfToken` (формата `число:число-balancer-...-BAL`) генерируется в JS-коде страницы и привязан к сессии. Достать его снаружи, **не исполняя JS, невозможно**.

### Что выбрал в итоге

Переключился на **headless-браузер (Selenium)**. Реальный Chromium сам получает все cookie, сессию и токены. Мы просто открываем страницу и читаем данные, которые уже есть в HTML.

**Как это работает:**

1. Открываем `https://yandex.ru/maps/org/x/{businessId}/reviews/?page=N` в headless-браузере.
2. Из HTML вытаскиваем `<script type="application/json" class="state-view">` – SSR-состояние с первыми 50 отзывами, рейтингом и счётчиками.
3. Для остальных страниц используем пагинацию через URL: `?page=1`, `?page=2`, ... до `min(600, totalPages)`.
4. Отзывы дедуплицируем по `reviewId`.

**Плюсы и минусы:**

| | |
|---|---|
| ✅ **Плюсы** | Не нужно разбираться с токенами. Устойчиво к изменениям в JS-логике. |
| ❌ **Минусы** | Медленно (~40–60 сек на организацию). Каждый парсинг запускает отдельный Chromium. |

### Устойчивость к смене разметки

Парсер **не молчит**, если что-то пошло не так. Он явно проверяет:

| Проверка | Код ошибки |
|---|---|
| Наличие `state-view` в HTML | `CODE_LAYOUT_CHANGED` |
| Наличие `stack[0].results.items[0].reviewResults` | `CODE_LAYOUT_CHANGED` |
| Наличие `ratingData` | `CODE_LAYOUT_CHANGED` |
| Длина HTML < 5000 байт | `CODE_BLOCKED` |
| Title содержит «Подтвердите» или «captcha» | `CODE_BLOCKED` |

Все ошибки пишутся в `parse_error` организации и в лог. Так сразу видно, что источник изменился, а не просто «0 отзывов».

### Антибан

- ⏱ **Пауза 800 мс** между страницами.
- 🌐 Подставляется **реальный User-Agent** Chrome.
- 🕵 В аргументы Chrome добавлен `--disable-blink-features=AutomationControlled`.
- 🚫 При `403/429` или заглушке `limited` выбрасывается `CODE_BLOCKED`, джоба повторяется.
- 🔄 **Для продакшена** пригодилась бы ротация прокси – в рамках тестового не делал.

## Фоновая обработка и идемпотентность

### Очередь

Парсинг вынесен в `ParseOrganizationJob` (Redis). Ключевые параметры:

- `$tries = 3` – три попытки при сбое.
- `$backoff = 30` – пауза 30 секунд между попытками.
- `$timeout = 300` – таймаут 5 минут.

В `config/queue.php` параметр `retry_after` увеличен до **350 секунд**, чтобы джоба не перезапускалась раньше времени.

Для 50 филиалов можно поднять несколько воркеров параллельно.

### Идемпотентность

При повторном парсинге **дубли не создаются**. В `OrganizationPersister` используется `updateOrCreate` по ключу `(organization_id, external_id)`. В миграции `reviews` есть уникальный индекс на эти два поля.

### История изменений (описана, но не реализована)

Для отслеживания «было → стало» я бы добавил таблицу `review_snapshots`:

- `review_id` (FK на reviews.id)
- `parsing_run_id` (FK на parsing_runs.id)
- `old_data` (JSON)
- `new_data` (JSON)
- `changed_at` (timestamp)

При каждом парсинге создаётся `parsing_run`, и для каждого изменившегося отзыва – запись в `review_snapshots`. Модель данных продумана, но реализовывать её в рамках тестового я не стал.

## Чему я научился в процессе

> **Пишу честно, потому что это важно:** Vue 3 и Selenium я до этого задания **не использовал**. Laravel знал на базовом уровне.

Что пришлось освоить:

- **Vue 3 Composition API, Vue Router, Pinia** – не понимал, как связать SPA-роутер с Sanctum, разбирался в `router.beforeEach` и `meta.auth`.
- **Sanctum в SPA-режиме** – долго не мог понять, почему логин через `curl` работает, а через браузер нет. Дело в `Origin`/`Referer` и CSRF-токене, который `axios` подставляет сам.
- **Selenium и headless-браузер** – понял, как работает WebDriver, `executeScript`, `executeAsyncScript`. Разобрался, почему важно подменять User-Agent: без этого Яндекс отдаёт заглушку `limited`.
- **Антибот-защита Яндекса** – узнал, что нельзя доверять токену из `state-view`, что правильный токен генерируется в JS, и что пагинация через URL – самый надёжный обход.
- **Очереди и отладка фоновых джоб** – столкнулся с `Job timed out`, узнал про `$timeout` и `retry_after`.
- **Идемпотентность через `updateOrCreate`** – осознал, насколько это важно для повторных парсингов.

## Deployment notes

Прототип развёрнут на VPS (1 GB RAM, Debian 12) без Docker – из-за ограничений по памяти. Стек: Nginx + PHP-FPM 8.4 + MariaDB + Redis + Chromium 152 (systemd-сервис) + Supervisor для очереди. Локально проект поднимается через Docker (Laravel Sail).

При деплое без Docker: заменить `SELENIUM_HOST` в `YandexMapsParser.php` на `http://localhost:9515`, настроить Nginx-vhost на `/public` с `fastcgi_pass unix:/run/php/php8.4-fpm.sock`.

**Ограничения хостинга:** 1 ГБ RAM – парсинг одной организации занимает 50–90 секунд. Параллельный парсинг невозможен.

## Известные ограничения

- ⚠️ Парсер **медленный** (~40–60 секунд на организацию) – осознанный trade-off в пользу надёжности.
